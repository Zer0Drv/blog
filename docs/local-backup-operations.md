# 本机隔离备份部署与验收（#58）

所有者于 2026-10-20 确认尚未配置备份，RPO 24 小时、RTO 2 小时，暂无独立存储和通知渠道。
本方案在 Docker 数据卷之外的 `E:\dev\zer0drv\backups` 保存受 ACL 保护的副本。
它能覆盖误删除/数据卷损坏等场景，**不能覆盖宿主机或 E 盘整体丢失**。不含异地副本与外部告警。

## 执行前提

先合并并部署两仓现场操作锁，暂停其他直接写 MySQL/MinIO 的运维任务，确认维护窗口。
本方案采用冷快照：按顺序停止后端、MySQL、Redis、MinIO，数据复制期间网站不可正常使用。
耗时取决于实际数据量；首次执行必须计时，不能预先承诺仅停几秒。
日常频率默认 02:00 和 14:00，每 12 小时一次，为 24 小时 RPO 留出重试余量。
若不接受停机，应另行实现已验证的在线一致性策略，不能直接去掉 stop。

需要稳定路径的 Python 3.11+、Docker Desktop、可用用户会话。计划任务使用当前登录用户，
机器休眠/关机或 Docker 不可用会失败；这不是无人值守服务器运行保障。

## 预览、首次执行与安装

```powershell
python E:\dev\zer0drv\blog\deploy\local-backup.py
& E:\dev\zer0drv\blog\deploy\install-local-backup.ps1

# 维护窗口中，审核上述计划后：
python E:\dev\zer0drv\blog\deploy\local-backup.py --execute
python E:\dev\zer0drv\blog\deploy\local-backup.py --status
& E:\dev\zer0drv\blog\deploy\install-local-backup.ps1 -Install
```

默认只预览，前两条命令不停止服务、不安装任务。首次执行成功且恢复验收通过后才安装计划任务。
安装器遇到已有同名任务会停止，避免覆盖运维设置。不要随意更改备份根目录：
其父目录的 `.deployment.lock` 必须与两仓 CD 一致。

快照覆盖 MySQL/Redis/MinIO 的完整持久目录、存在时的本地上传目录、实际容器配置、`.env`、
Compose 与网关配置，记录镜像 ID/可拉取 digest、恢复点和各成员 SHA-256。
Redis 草稿与安全状态不会被当作可丢缓存。当前只读盘点未发现 `/app/uploads`，每轮仍重新检查。
**runtime-config.json、deployment.env 和归档均含敏感数据，不能上传 GitHub/CI 或发到聊天。**
快照只允许当前账户与 SYSTEM 访问；SHA-256 用于完整性，不提供来源认证或静态加密。

复制或校验失败仍尝试恢复所有已停止服务，并逐一等待健康；失败返回非零且保留上一成功记录。
`last-attempt.json` 记录本轮状态，`last-success.json` 只在完整校验和服务恢复通过后更新。
每小时状态任务检查最后完整恢复点的年龄；超过 18 小时或最近备份失败，任务返回非零。
查看 Windows 任务计划程序的最后运行结果与上述文件处理故障；目前**没有外部主动通知**。

## 保留与容量

建议至少保留 14 天、每日至少一个成功恢复点；最初不自动删除，先测量单次体积并预留
至少 28 份快照空间。容量不足时本轮失败，不牺牲旧副本换取成功标记。
运维人员在确认更新副本完整且已恢复验收后，才能清理过期恢复点；长期自动轮换尚未启用。
停止服务前按文件逻辑大小估算容量，要求至少两倍源数据体积加 5 GiB 剩余空间，
避免稀疏数据库文件归档展开后耗尽宿主盘。计划任务失败后间隔 5 分钟最多重试三次。

## 隔离恢复验收

1. 从宣布恢复开始计时，验证目标快照：
   `python deploy/local-backup.py --verify <完整快照目录>`。
   缺件、额外成员、损坏或路径越界立即中止；校验通过不等于数据已恢复可用。
2. 建立全新的 `blog-restore-<UUID>` Compose 项目、命名卷和 loopback 高端口；
   只能使用清单中的原始 MySQL/Redis/MinIO 镜像 digest。不要把冷备文件写入运行中的服务。
   物理 MySQL 副本不跨大版本升级，不让新后端对恢复库自动运行未经确认的迁移。
3. 在停止的隔离容器中展开对应 tar，保留目录布局和权限；本地附件恢复到新目录。
   核对实际运行配置与 `.env`，恢复 TOTP/JWT 等必要密钥。禁止覆盖生产库、桶和目录。
4. 先启动隔离基础设施并确认健康，再启动兼容后端；关闭邮件/订阅 worker 等外部副作用，
   保留恢复的 Redis 草稿与安全状态。网关使用恢复的前端资源与隔离 API。
5. 验证登录/TOTP、公开及受限文章、版本历史/回收站、附件字节与引用、全文搜索和 schema。
   记录数据量、取得备份/镜像/密钥、展开、启动和业务验收的耗时，端到端应不超过 2 小时。
6. 只有所有者验收后才考虑切换。保留原实例，不自动覆盖或降级 schema；
   清理只针对本轮 UUID 项目，不使用生产 Compose 的 `down -v`。

现有合成数据逻辑恢复演练仍见 [backup-restore-drill.md](backup-restore-drill.md)。
本脚本的单元测试验证完整性、失败后恢复服务与成功记录，不替代本轮物理副本的实际恢复。
首次生产备份、隔离恢复计时、定时任务启用、异地存储和外部告警均须分别记录真实执行状态。
