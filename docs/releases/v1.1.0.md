# v1.1.0 发布说明与准备

本轮按所有者确认的范围，只收录自 v1.0.0 后已合并的交付。CHANGELOG 中的 2026-10-16 是本轮准备的计划发布日期；若正式发布跨日，应先修正日期，再创建 tag。本说明和 CHANGELOG 随发布准备 PR 提交；正式 tag 须包含它们，不能先打在旧提交上。

## 版本范围

两仓配套提供 slug 固定链接、密码/私密文章、Markdown/front matter 与批量 zip、友情链接、自定义页面与导航、文章订阅、系统参数配置和附件观察期清理；同时包含编辑保存、会话吊销、分类清空、附件清理与发布故障修复。逐项实现链接见本仓 [CHANGELOG](../../CHANGELOG.md)。

TOTP（[blog#19](https://github.com/Zer0Drv/blog/issues/19)）、AI 增强（[blog#21](https://github.com/Zer0Drv/blog/issues/21)）未实现，按本次决定顺延，不纳入 v1.1.0。双 token / refresh rotation（[blog#26](https://github.com/Zer0Drv/blog/issues/26)）也不在此版本。

[blog#58](https://github.com/Zer0Drv/blog/issues/58) 只计入已完成的真实依赖回归和两侧发布门禁；网关业务冒烟、前后端 SHA/schema 兼容记录、历史产物认证、真实浏览器 E2E、恢复演练与体验基线等剩余项继续跟踪。已有功能 Issue 的验收/关闭决定不由打 tag 代替。

## 升级与回滚

先部署后端，确认 Flyway V10–V16（友链、slug、可见性、页面、订阅、系统参数、附件清理）及新 API 可用，再部署前端，避免管理页先引用缺失接口。真实升级测试覆盖从 V13/V15 的代表性数据升级，并不等于对生产全部数据或备份恢复作出保证。

所有后端实例升级到支持引用锁的版本后，再启用附件扫描/物理清理。普通删除只移出附件库；物理删除由管理员在至少 7 天观察期后复检执行。已经物理删除的对象不能通过回滚应用恢复。

回滚仍选择经过核对的 `sha-<8位>` 历史镜像/前端归档；Git 的 `v1.1.0` 不是现有 CD 的 rollback_tag 输入。应用回滚不回退 Flyway schema，也不恢复数据库、Redis 或对象存储数据。

## 创建正式版本

1. 所有者审核合并两仓发布准备 PR，并确认本轮功能验收及计划日期；未完成需求保持开放。
2. 获取两仓各自最终的 main 合并提交，核对该提交完整 CI 成功；记录两个完整 SHA，不能直接沿用上表的准备基线。
3. 分别在已核实的 main 提交上创建不可移动的附注 tag `v1.1.0`，发布说明取本仓 CHANGELOG 的 1.1.0 章节，并链接另一仓对应版本。不改写既有 v1.0.0。
4. 当前 CD 只响应符合路径过滤的 main push 或手动执行，创建 Git tag 不会自动部署。若要将最终 tag 提交作为实际发布产物，应从 main 手动运行正常 CD，经过完整 CI、同 SHA 产物校验与 production 审批，并在 [发布准备 Issue](https://github.com/Zer0Drv/blog/issues/72) 回填运行及产物证据。
5. 仅在正式 tag/发布记录已建立且版本范围核对后关闭对应里程碑；Issue 是否关闭仍按自身验收决定。
